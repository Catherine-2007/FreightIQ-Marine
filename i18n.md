# FreightIQ Marine — Internationalization (i18n)

## What's covered in this build

`frontend/assets/js/i18n.js` defines `FIQ_LANGUAGES` (17 languages) and
`FIQ_TRANSLATIONS` (a key → string dictionary per language). On page load,
every element with a `data-i18n="some_key"` attribute has its text replaced
with `FIQ_TRANSLATIONS[currentLang][some_key]` (falling back to English).
This covers:

- Sidebar navigation labels
- Common buttons (Sign In, Sign out, Export CSV, Print/Save as PDF, Submit…)
- Common field labels (Email, Password, Status, Language, Currency, Theme…)
- The login/register page tagline

Urdu (`ur`) and Arabic (`ar`) additionally flip `<html dir="rtl">` so the
whole layout mirrors correctly.

## What's intentionally NOT translated in this build

Server-generated explanatory text is not translated:

- Forecast reasoning sentences (`ForecastEngine`, `MarketEntryEngine`)
- Risk detail sentences (`RiskEngine`)
- Vessel-recommendation reasons (`VesselOptimizer`)
- Alert/notification messages seeded in the database
- Table column headers rendered directly in JS template strings (e.g. the
  Fleet roster table headers are static PHP, not yet wired to `data-i18n`)

This is a deliberate scope decision, not an oversight: these strings are
generated dynamically from live data (dates, numbers, port names, computed
scores) and would need either (a) a server-side translation layer per
language, or (b) restructuring every engine to emit translation keys + data
separately from prose. Both are reasonable next steps — see below.

## Extending translated coverage

**To add a new UI chrome string:**
1. Add the key to every language block in `FIQ_TRANSLATIONS` (at minimum,
   add it to `en` — missing keys fall back to English automatically).
2. Add `data-i18n="your_key"` to the element in the relevant `.php` page.

**To add a new language:**
1. Add `{ code, name, native }` to `FIQ_LANGUAGES`.
2. Add a full key set to `FIQ_TRANSLATIONS[code]` (copy the `en` block as a
   starting template so no keys are missing).
3. If the language is RTL (e.g. Hebrew, Persian), add its code to
   `FIQ_RTL_LANGS`.

**To translate dynamic/generated content:**
The cleanest approach is to make each backend engine return a translation
*key* plus structured data instead of a finished English sentence — e.g.
`ForecastEngine::predictHorizon()` could return
`{'entry_window_key': 'favorable_falling_rates', 'entry_window_args': {...}}`
instead of a hard-coded English string, and the frontend would render that
key through the same `FIQ_TRANSLATIONS` dictionary. This is a larger refactor
than the UI-chrome translation covered here, so it's left as a documented
next step rather than attempted partially.

## Update: extended coverage (current state)

`frontend/assets/js/i18n_ext.js` (generated — do not hand-edit) adds **138 keys**
to each of the 17 languages: page titles & subtitles, buttons, form labels,
table headers, section titles, KPI labels, status / risk-level enums, the
Digital Twin panel and the digital-twin disclaimer. Source of truth is
`docs/i18n_data/<lang>.txt` (one line per section, `|`-separated values) and
`docs/i18n_data/build.py`, which **asserts every section's value count** so a
missing or extra value can never silently shift later translations:

    python3 docs/i18n_data/build.py frontend/assets/js/i18n_ext.js

Database enum values (statuses, risk levels) are translated **for display
only** via `fiqEnum()`; the stored values and CSS class names stay English.

Dynamic content re-renders on language change: `fiqSetLanguage()` dispatches
`fiq-lang-changed` and the generic `fiq-refresh-money` re-render signal.

**Still English (by design):** server-generated explanation sentences
(forecast/risk/optimizer reasons), seeded alert & notification messages, and
a few rarely-seen labels (e.g. "Failed Attempts", "Cause"). 

**Translation quality:** these translations are machine-assisted and have not
been reviewed by native speakers — especially for lower-resource languages
(Odia, Assamese, Punjabi, Malayalam). Have native speakers review
`docs/i18n_data/*.txt` before any production use.

## Update v3: universal coverage via auto-translation

`frontend/assets/js/i18n_auto.js` (**generated** — do not hand-edit) makes every page multilingual,
not only elements with `data-i18n`:

* It indexes every English value in `FIQ_TRANSLATIONS.en` **plus 96 extra phrases** (table headers,
  empty-states, admin actions, report names, login/register copy, Load Lab, Time Machine, palette…).
* It walks the DOM and a `MutationObserver` watches for new nodes, so tables/badges/popups built in
  JS template strings, Leaflet tooltips, toasts and modals are translated as they appear.
* Text, `placeholder`, `title`, `aria-label`, `alt` and the browser-tab title are covered. Leading
  emoji and trailing `…` `:` `→` and `(COA)`-style suffixes are tolerated.
* Original English is remembered per node, so en → hi → ar → en never drifts or sticks.
* New JS code can call `fiqX('English phrase')` to translate on the fly.

**Add or fix a phrase:** edit `docs/i18n_data/extra_phrases.txt` (one line,
`English|hi|bn|te|mr|ta|gu|kn|ml|pa|or|as|ur|es|fr|ar|zh` — exactly 17 fields), then run

    python3 docs/i18n_data/build_auto.py

The build asserts the field count of every line.

**Still English by design:** sentences generated by the PHP engines (forecast/risk/optimizer
reasons, seeded alert text) — see "Extending translated coverage" above. The engine only swaps
*exact* known phrases, so unknown text safely stays English instead of being mistranslated.
**Quality:** the new phrases are machine-assisted and not reviewed by native speakers — have them
reviewed before production use (especially Odia, Assamese, Punjabi, Malayalam).

## Update v4: sentence templates + content coverage
Phrase files merged by `build_auto.py`: `extra_phrases.txt`, `sentences.txt` … `sentences5.txt` (268 entries × 16 languages).
Entries containing `{1}`, `{2}`… are **templates**: e.g. `Forecast confidence: {1}%, volatility: {2}%.` matches the backend
sentence with any numbers/names, and the captured values are re-inserted (and themselves translated when they are
known words such as *High*, *Rising*, *Clear*). The build fails if a translation drops a placeholder.
`fiqLocale()` (in `i18n.js`) gives the BCP-47 locale so dates/clock follow the UI language.
Proper nouns (ports, routes, vessels, people, companies) and technical abbreviations (IMO, LOA, ETA, AIS, COA, CSV, currency codes) stay as written.
Machine-assisted translations: have native speakers review before production use.
